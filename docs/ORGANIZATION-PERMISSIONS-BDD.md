# 组织架构、数据权限与数据汇总 BDD 说明书

更新：2026-09-05。适用页面：A 拓扑结构 /organization/figma。读者：产品、开发、测试及接入其他业务系统的 Agent。

BDD（行为驱动开发）用“假如 Given / 当 When / 那么 Then”描述可验收的行为。本说明书是组织权限方案与后端验收设计，不是已经上线的授权引擎，也不是自动执行的测试报告。

## 1. 先区分已确定设计、当前 UI 与生产要求

| 标记 | 含义 | 本文使用方式 |
| --- | --- | --- |
| 已确定设计 | 本次讨论已经确定的业务原则 | 多名平级负责人、多任职、范围并集、标签不授权、HRM 只管系统准入，本系统管页面和按钮 |
| UI 已实现 | 当前页面可以操作的前端演示 | 页面权限树、现场配置、角色/人员测试、人员角色分配；功能权限存本标签页 sessionStorage，组织数据范围和标签仍只存页面内存 |
| 生产要求 | 接入真实系统必须满足的安全或正确性约束 | 服务端鉴权、系统隔离、稳定标识、撤销生效、去重、审计 |
| 待确认 | UI 无法回答或尚未批准的业务政策 | 历史归属、共享业绩分摊、显式拒绝优先级、敏感字段等 |

当前 UI 已模拟本系统功能角色并集、页面访问拦截和已登记按钮开关；没有真正过滤业务数据、计算数据范围并集、调用 HRM 或执行服务端访问控制。组 KPI 和部门 KPI 来自示例快照，不是根据画面上的人员卡实时算出。36 人是源示例汇总，15 条成员卡是节选，不能从节选名单推导真实组织人数。

本文数字案例均为独立的虚构测试数据，不对应示例页面上的真实业绩。下面的生产 BDD 必须由目标系统实现并测试，不能因为文档或按钮存在就宣布验收通过。

## 2. 术语与职责边界

| 概念 | 准确定义 | 不应混淆成什么 |
| --- | --- | --- |
| 组织节点 orgId | 部门、业务组等稳定节点；形成上下级树，承载归属与汇总范围 | 不是一个只能放一人的岗位，也不是某个人的名字 |
| 人员 personId | 跨任职、跨层级保持一致的人员身份 | 不是姓名、工号展示文本、卡片行号 |
| 任职 appointmentId | 某人在某节点担任负责人或组员的一条关系，有有效期与状态 | 不是新增一个人；同一人可以有多条有效任职 |
| 节点负责人 | 任职关系中的负责人类型；可以显示组长、队长、部门经理等称谓 | 不由 KA 标签决定，不自动等于系统管理员 |
| 基础查看范围 | 看本人 / 看本人及下级 / 看本系统全部 | 不是修改、删除、导出或审批权限 |
| 额外组织范围 | 在任职基础范围之外，显式补充可查看的组织及其后代 | 不改变任职、人员归属或业绩归属 |
| 人员识别标签 | KA、质检等稳定编码与可修改名称，按人员身份共享 | 不是本系统功能角色，不隐式授予任何权限 |
| HRM 系统准入 | 账号是否有效、人员能否进入指定业务系统 | 不管理系统内部页面和按钮 |
| 本系统功能角色 | 本系统页面访问、按钮和动作授权；多角色取并集 | 不自动扩大数据查看或修改范围，也不覆盖 HRM 准入拒绝 |
| 数据事实 factId | 一条可计量的业务记录，如订单、任务或业绩记录的稳定唯一身份 | 不是负责人卡片、查询 JOIN 结果中的一行 |
| 数据归属 | 事实属于哪个组织、哪个人员以及哪个业务期间 | 不是谁恰好能看见这条数据 |
| 汇总节点 | 按组织归属汇集自己和后代节点事实的节点 | 数据不需要复制给每位负责人 |

组织结构回答“谁在哪里任职、这个节点下面有哪些节点”；任职类型回答“谁是负责人或组员”；查看范围回答“能看到哪些数据”；HRM 回答“能不能进入本系统”，本系统功能角色回答“能执行什么动作”；业务事实归属回答“这份业绩计入哪里”。这些关系需要分别保存，不能用一个“角色”字段包办。

## 3. 建议的数据契约与服务端计算顺序

以下是接入建议，不是当前前端已存在的数据库表。字段名称可以随既有架构调整，但稳定标识、系统边界与有效状态不能丢失。

| 对象 | 最少应表达的信息 |
| --- | --- |
| Organization | orgId、parentOrgId、名称、启用状态；共享组织目录与业务系统的适用关系 |
| Person / Account | personId、登录账号到人员的可信映射、账号与人员状态 |
| Appointment | appointmentId、personId、orgId、负责人或组员类型、有效起止时间、状态 |
| DataScopePolicy（查看策略） | applicationId、appointmentId、SELF / SELF_AND_DESCENDANTS / ALL、额外组织根节点集合、版本；写操作范围另行建模 |
| PersonTag | personId、tagCode；标签库另存 tagCode、名称、状态 |
| BusinessFact | applicationId、factId、归属 orgId、可用时的归属 personId、业务时间、指标字段与数据状态 |
| PermissionSnapshot / Audit | 主体、系统、动作、任职与策略版本、允许或拒绝原因、变更人及时间 |

当前 UI 用节点 + 任职类型 + 人员 ID 区分配置，只适合示例。生产应采用独立 appointmentId，否则同一人在同一节点离任后再次任职、并行任职或追溯历史时容易串用旧配置。

建议计算步骤：

1. 从可信登录态解析 personId 与当前 applicationId；验证账号、人员状态，不相信客户端传来的“管理员”或人员 ID。
2. 加载当前有效任职及该业务系统的策略；不存在的任职、已撤销任职或跨系统策略不能参与授权。
3. 对每条任职展开基础范围，再展开额外组织根节点及后代；组织关系必须经过合法性校验。
4. 对所有有效任职的查看范围取集合并集；“看本人”的窄范围不抵消另一条有效任职的宽查看范围。
5. 先校验 HRM 系统准入，再校验本系统功能角色对页面和读取动作的授权，再在服务端限定数据查询；默认拒绝无法证明允许读取的记录。
6. 查询详情、列表、搜索、总数、图表、只读批量查询与导出复用读取边界；导出仍需独立的本系统导出权限，不能先泄露总量再隐藏明细。编辑、删除、审批及批量写入必须另行定义动作专属的数据范围，不能自动复用本 UI 的查看范围。
7. 汇总使用已确定的业务事实归属与统计口径，事实去重后聚合；查看授权不改写归属。
8. 返回必要数据与安全的范围说明；记录可审计的判定依据，不把无权查看的姓名、金额或组织结构塞入错误详情。

```text
任职查看范围 = 基础查看范围 ∪ 额外组织后代范围
个人查看范围 = 并集（当前系统内，各有效任职查看范围）
允许读取某条记录 = 身份有效 AND HRM允许进入当前系统 AND 本系统角色允许当前页面及读取动作 AND 记录属于当前系统 AND 记录在个人查看范围
节点汇总 = 按统计期间筛选后，汇集节点自身及后代的归属事实，按事实唯一键去重后聚合
```

这套最小模型目前只有“允许查看范围”，没有配置显式 deny 的界面，也没有规定写操作范围。若未来加入拒绝规则，不可自行假定“拒绝优先”或“最宽优先”；必须先确定冲突政策，增加版本与回归用例。

“本人数据”应由目标系统明确映射到事实归属字段。例如订单负责人、店铺负责人、创建人不是天然等价；下面案例暂以 ownerPersonId 表示已确认的本人归属字段，不能直接将 createdBy 当作本人范围。

## 4. 一套可以手算的完整案例

测试业务系统 S1 下有 D 运营部，下面有 A 组和 B 组。甲、乙是 D 的平级负责人，甲同时也是 A 的负责人。丙是 A 的组员，丁是 B 的组员；乙还在 B 任负责人。四个稳定人员 ID 对应六条任职，实际独立人数仍为四人。

下面四条事实都属于 S1；同一 factId 可能因为多负责人 JOIN 在查询结果出现多行，但只代表一条事实。

| factId | 归属组织 | 归属人员 | 金额 |
| --- | --- | --- | --- |
| F1 | A | 甲 | 100 |
| F2 | A | 丙 | 200 |
| F3 | B | 丁 | 300 |
| F4 | D（部门直属） | 乙 | 40 |

正确汇总：A = 100 + 200 = 300；B = 300；D = 300 + 300 + 40 = 640。D 的甲、乙各自看到同一份 640，并不意味着部门业绩变成 1280。甲同时担任 A 负责人也不会让 F1、F2 再计一次。

为单独检验组内权限，将甲的 D 任职临时配置为“看本人”，A 任职配置为“看本人及下级”。甲的最终可见事实为 F1、F2，金额 300；D 任职的“看本人”没有把 A 的 F2 排除。若 D 任职改回“看本人及下级”，最终变为 F1、F2、F3、F4，金额 640。

丙默认“看本人”，只能看 F2 的 200。给丙额外授权 B 后，可以看 F2、F3，共 500；但 A 的归属业绩仍为 300，B 仍为 300，D 仍为 640。丙并未成为 B 负责人，丁也未变成丙的组织下属。

给丙配置“看本系统全部”，在具有 S1 查看功能权限时可看 640。另一个系统 S2 即使也有组织 A、人员丙或类似工号，其事实都不进入本次结果。若 S1 还有组织树之外合法归属的业务记录，“本系统全部”覆盖的是 S1 全部业务数据，不能偷偷缩成当前 D 子树；敏感字段和动作授权仍需单独控制。

## 5. BDD：任职与基础数据权限

### P01 同一节点有多名平级负责人【已确定设计】

- 假如 Given：甲、乙都在 D 担任有效负责人，各配置看本人及下级，且都具备 S1 报表查看权限。
- 当 When：两人分别打开 D 的数据。
- 那么 Then：两人都能看到 D 自身及 A、B 的 640；没有主次负责人、五五分摊或因第二位负责人加入而重复汇总。

### P02 同一人跨层或跨组任职【已确定设计】

- 假如 Given：甲有 D 和 A 两条独立有效任职；也允许同一人同时在 A、B 平级任职。
- 当 When：修改 A 任职的查看范围。
- 那么 Then：只修改 A 的配置；最终个人范围取所有有效任职并集。另一次宽范围任职仍可能使甲看到 A 的全部数据，不能把单张卡的窄配置误认为全局限制。

### P03 负责人只看本人【已确定设计】

- 假如 Given：甲仅有 A 的有效负责人任职，配置为看本人，且没有额外组织授权。
- 当 When：甲查看本例数据。
- 那么 Then：只返回 F1 = 100，不返回丙的 F2；甲仍是 A 负责人，职责身份没有因缩小查看范围而改变。

### P04 负责人看本人及下级【已确定设计】

- 假如 Given：甲仅有 A 的有效负责人任职，配置看本人及下级。
- 当 When：服务端解析范围。
- 那么 Then：包含本人及当前任职节点所辖数据；本例返回 F1、F2 = 300。若 A 下未来存在子节点，应沿合法后代关系递归覆盖，不只查直接人员。

### P05 组员选择本人及下级【已确定设计 / UI 已实现】

- 假如 Given：丙是普通组员，没有另行建模的下级任职或负责节点。
- 当 When：在丙的组员卡选择看本人及下级。
- 那么 Then：仍只覆盖本人 F2 = 200；不能因为丙属于 A 就授予 A 全组数据，也不能把平级组员当下级。

### P06 看本系统全部【已确定设计 / 生产要求】

- 假如 Given：丙的一条有效任职在 S1 配置 ALL，且 HRM 允许进入 S1、本系统角色允许 S1 报表查看。
- 当 When：查询 S1 数据或伪造请求尝试读取 S2。
- 那么 Then：S1 查询可以覆盖当前业务系统全部数据；S2 不能靠 S1 的 ALL 获得授权。ALL 不赋予组织编辑、删除、导出、审批或修改授权的能力。

### P07 有范围但没有功能权限【已确定设计 / 生产要求】

- 假如 Given：甲具有 D 全范围，HRM 允许其进入系统，但本系统角色未授予报表查看或已撤销该动作。
- 当 When：通过页面或直接调用报表 API。
- 那么 Then：拒绝该动作，不返回 640 的汇总或明细；按钮隐藏只改善体验，API 必须独立拒绝。

### P08 有功能权限但没有数据范围【生产要求】

- 假如 Given：某账号具有报表查看功能，却没有可验证的有效任职与适用数据授权。
- 当 When：请求某组织报表。
- 那么 Then：不能因为“能进页面”而看到整个组织的数据；请求拒绝或返回受控空结果的产品表现可约定，但不能扩大范围。

## 6. BDD：额外组织树与人员识别标签

### P09 额外选择组织只增加可见范围【已确定设计】

- 假如 Given：丙的基础范围为本人，额外勾选 B。
- 当 When：查看业务记录与组织业绩。
- 那么 Then：个人可见 F2、F3 = 500；A/B/D 归属汇总仍为 300/300/640，丙的任职和人员归属不变。

### P10 勾选父级包含未来后代【已确定设计 / UI 已实现】

- 假如 Given：额外组织保存的是 D 这个根节点，当前包含 A、B。
- 当 When：D 下新增 C，且 C 对当前系统有效。
- 那么 Then：D 的额外范围自动包含 C；保存意图是“D 及后代”，不是保存当时 A、B 的静态列表。跨业务系统的数据仍不能进入。

### P11 父级全选后取消一个子组【已确定设计 / UI 已实现】

- 假如 Given：额外组织选中 D，取消 A。
- 当 When：保存，再给 D 新增 C。
- 那么 Then：当前两级 UI 把选择改为显式 B，不再保留 D 的全部后代意图；后来新增 C 不自动获权。树上 D 显示半选，右侧显示 B。

### P12 搜索与选择范围互相独立【UI 已实现】

- 假如 Given：搜索中文组织名或拼音缩写，只显示命中的子组与其父路径。
- 当 When：在搜索结果中勾选部门父节点。
- 那么 Then：仍选择该部门的全部下级及未来子组，不只选择搜索结果；清空搜索不会改变已选授权。无结果不会清空原选择。

### P13 逐个勾完当前子组不自动升级授权【UI 已实现】

- 假如 Given：显式选择所有当前子组。
- 当 When：保存后给部门新增 C。
- 那么 Then：仍保存显式子组名单，父级显示半选，C 不自动获权。只有主动勾选部门才表示包含未来子组；不能为了压缩已选项而把名单归一化成父级，从而悄悄扩大授权。

### P14 任职撤销时额外授权随任职失效【生产要求】

- 假如 Given：丙的 B 额外授权保存在 A 的某条任职上。
- 当 When：该任职到期或被撤销。
- 那么 Then：该条任职的基础范围与额外范围一起停止参与并集；丙其他有效任职产生的合法授权保留，不残留已撤销任职的范围。

### P15 KA 只是标签【已确定设计 / UI 已实现】

- 假如 Given：给甲添加 KA，甲在 D 与 A 的卡片使用同一 personId。
- 当 When：查看两张卡或其他程序读取人员标签。
- 那么 Then：两处同步显示 KA，其他程序通过稳定编码识别甲；原数据范围与 本系统动作权限不变，甲不会自动成为组长、管理员或获得跨系统数据。

### P16 标签改名不改变身份编码【UI 已实现】

- 假如 Given：已有编码 KA 的标签，名称为 KA。
- 当 When：改名为重点客户人员并保存。
- 那么 Then：绑定仍引用 KA，其他系统不应靠显示名识别；重复编码被拒绝。生产若要按标签触发业务流程，必须在消费系统显式定义规则，不能推导成数据授权。

## 7. BDD：数据汇总、去重与指标口径

### A01 汇总节点包含自己与后代【已确定设计】

- 假如 Given：本例存在 A/B 组事实和 D 直属 F4。
- 当 When：计算 D 金额。
- 那么 Then：结果为 640，不能漏掉直属 40；空的负责人列表不意味着组织没有数据。

### A02 多负责人、多任职与 JOIN 不重复计业绩【生产要求】

- 假如 Given：F1、F2 因 A 有两名负责人或甲跨层任职，在 JOIN 后各出现两次。
- 当 When：汇总 A、D 或个人查看范围内的数据。
- 那么 Then：先按业务系统内稳定事实唯一键去重，A 为 300、D 为 640。不能使用 SUM(DISTINCT 金额)，因为金额相同但 factId 不同的事实必须都计入。

### A03 人数去重与业绩去重是两回事【已确定设计 / 生产要求】

- 假如 Given：甲乙丙丁四个 personId 对应六条任职。
- 当 When：计算组织覆盖的独立人员数量。
- 那么 Then：按 personId 集合得四人，不按卡片或 appointmentId 数六人；金额仍按 factId 去重，不能按人员去重后丢掉同一人的多笔事实。正式人数是否仅算在职员工、兼任者或外包人员，须确认名单口径。

### A04 比率必须由分子分母重新计算【生产要求】

- 假如 Given：A 完成 80/目标 100，完成率 80%；B 完成 9/目标 10，完成率 90%；指标定义允许合并这些分子分母。
- 当 When：计算合计完成率。
- 那么 Then：先合计为 89/110，结果约 80.91%，不能平均两个百分比得 85%。若指标是评分而非可加分子分母，则按业务指定权重算法，不能套用本例。

### A05 空值、零值与未知不能互换【生产要求】

- 假如 Given：某组织目标或实际值未知为 null，另一个组织真实实际值为 0。
- 当 When：展示指标或汇总。
- 那么 Then：真实零值保留 0；未知显示待统计，不偷偷补 0。分母为 0 时不产生 Infinity 或伪造 0%。能否汇总已知部分、如何标记不完整与覆盖率，需要指标规则明确；没有规则时不得展示成完整结果。

### A06 看到谁的数据不决定汇总给谁【已确定设计】

- 假如 Given：给丙额外授予 B 或 ALL，且组织归属没有变化。
- 当 When：再次计算 A、B、D 业绩。
- 那么 Then：各结果不变。所谓“汇总到负责人那里”是负责人读取其负责节点的汇总，不是把数据转移或复制到负责人名下。

### A07 汇总卡不能绕过明细范围【生产要求】

- 假如 Given：丙只允许看 F2，却可打开含组织汇总卡的页面。
- 当 When：请求 A 总数、金额、图表、筛选选项或导出预览。
- 那么 Then：不能泄露包含 F1 的全组 300。若展示授权范围内统计，应明确标成“当前可见范围 200”；如果业务希望允许看总量但不看明细，必须新增独立授权政策，不能默认放行。

### A08 共享事实与业务归属分摊【待确认】

- 假如 Given：一笔金额 100 的业绩需要同时关联 A、B。
- 当 When：决定组业绩与部门业绩算法。
- 那么 Then：先确定它是主归属、分摊（如 60/40）还是两个分析视角。未确认前不能让 A、B 各计 100 后再相加成部门 200。若采用分摊，必须保存分摊记录与权重校验；部门仍不能重复计原始事实。

## 8. BDD：组织维护、任职变化与历史

### L01 编辑组织名称保持稳定身份【生产要求】

- 假如 Given：额外范围、任职、历史事实都引用 A 的 orgId。
- 当 When：把 A 改名为新名称。
- 那么 Then：引用和业绩不变，展示与组织搜索更新；不得按名称重建节点或把旧名当作失效授权。

### L02 删除不是隐藏卡片【生产要求】

- 假如 Given：组织节点仍有下级、有效任职、人员、数据事实、授权引用或历史引用。
- 当 When：请求删除节点。
- 那么 Then：服务端检查依赖并拒绝未处理的删除，不自动连带删除人员或业绩，不把遗留人员提权到上级。界面应说明阻塞原因与需先处理的关系；前端禁用按钮不能代替服务端校验。

### L03 空节点与根节点删除【生产要求 / 待确认】

- 假如 Given：节点没有下级、人员、任职及已知依赖。
- 当 When：有组织删除功能权限的人确认删除。
- 那么 Then：普通空节点可按已确认的删除策略处理；生产仍需在事务内复核关联数据与并发变化。历史记录存在时采用停用还是软删除、唯一根部门是否允许删除，须先确认；不能把当前 UI 看起来“空”当作数据库无引用的证明。

### L04 防止组织循环、孤儿和跨边界挂接【生产要求】

- 假如 Given：组织 A 下有子节点 C，或请求指定一个不存在/不可用的父节点。
- 当 When：尝试把 A 挂到 C 下、自己挂自己、引用不存在的父节点或越过隔离边界。
- 那么 Then：拒绝保存；不会无限递归、生成孤儿或扩大数据范围。正常多层树应支持递归查询并检测异常。

### L05 人员调动后的当前授权【生产要求】

- 假如 Given：丙从 A 调到 B，旧 A 任职正式结束，新 B 任职按流程生效。
- 当 When：丙再次访问数据。
- 那么 Then：旧任职及其额外范围不再参与当前授权；新任职使用独立配置或经确认的默认规则，不按姓名或人员 ID 偷偷继承旧任职宽权限。当前 UI 调岗只是演示名录移动，不代表上述生命周期已实现。

### L06 历史业绩归属与历史查看范围【待确认】

- 假如 Given：丙在 8 月于 A 产生 200 的业绩，9 月调入 B。
- 当 When：查询 8 月报表或甲、乙查询历史数据。
- 那么 Then：必须分别确认“业绩按发生时归属还是按现组织重算”与“历史数据谁能看”。二者不是同一个问题；不得因为当前人员移动就回写历史事实。建议保留事实发生时归属及组织/任职有效期，最终政策由业务确认。

### L07 无负责人或空业务组【已确定设计 / 生产要求】

- 假如 Given：新建业务组没有负责人、成员和已知 KPI。
- 当 When：渲染或查询该组。
- 那么 Then：组织仍是有效节点，可显示待指定负责人、待统计；不会凭空创建负责人或把未知 KPI 当 0。授权给祖先节点的合法人员仍可覆盖该组织；不能为了“无人负责”自动授权所有人。

### L08 离职、账号禁用与代理任职【生产要求 / 待确认】

- 假如 Given：人员离职或账号被禁用，即使其历史任职还存在。
- 当 When：其会话、旧链接或后台导出任务再读取受保护数据。
- 那么 Then：身份有效性校验阻止新的访问，历史事实保留。临时代理、请假代管需要带有效期的明确授权，不通过临时改标签代替；代理功能尚未定义，不能默认为已有。

## 9. BDD：授权治理与 API 验收

### S01 未授权用户不能给自己扩权【生产要求】

- 假如 Given：普通用户只能查看本人，没有权限配置管理能力。
- 当 When：直接提交 ALL、修改 appointmentId、额外组织 ID 或别人 personId。
- 那么 Then：服务端拒绝越权配置；有配置管理能力也只能在其可授予范围内操作。前端演示中的示例管理员不是生产身份凭据。

### S02 撤销与缓存一致性【生产要求】

- 假如 Given：某条宽授权被撤销，但旧权限快照、报表缓存和登录会话仍存在。
- 当 When：后续受保护请求发生。
- 那么 Then：服务端不能继续信任失效版本；需通过版本校验、失效通知或其他可证明的机制使撤销生效。可接受的延迟、缓存键及在途任务处理必须明文约定；授权不可用时不得回退为全部数据。

### S03 列表、详情、导出与只读批量接口一致【生产要求】

- 假如 Given：丙不能看 F1，只能看 F2。
- 当 When：尝试猜 F1 ID、改变分页参数、搜索 F1、导出或批量读取 F1/F2。
- 那么 Then：各读取入口都校验当前系统、对应读取或导出动作与记录查看范围。只读批量请求是整体拒绝还是返回允许子集须有明确接口契约，并防止用失败信息枚举无权数据。批量编辑、删除和审批不适用这个读取公式，必须校验另行定义的动作专属数据范围。

### S04 异步导出与下载链接【生产要求】

- 假如 Given：甲有权限时提交导出，生成或下载前权限被撤销。
- 当 When：任务执行或领取文件。
- 那么 Then：按已约定的时点策略复核授权，不能用永久公开链接绕过撤销。导出动作还需 本系统功能角色独立允许，不能因为能看就能导出。

### S05 并发修改、审计与版本【生产要求】

- 假如 Given：两名管理员同时编辑任职范围或一人删除节点而另一人新增成员。
- 当 When：提交冲突变更。
- 那么 Then：通过事务与版本校验阻止静默覆盖和悬空引用；记录操作者、被修改主体、系统、前后范围、时间与理由，便于解释“为什么此人能看见这条数据”。

### S06 字段与动作仍有各自边界【生产要求 / 待确认】

- 假如 Given：用户允许读取某条组织数据，但其中含手机号、薪资或其他敏感字段。
- 当 When：业务接口返回或执行修改、删除。
- 那么 Then：查看范围不自动允许所有字段及写操作。敏感字段脱敏、字段授权、写入所用数据范围、审批和职责分离规则需要另定；这套 UI 目前仅配置查看范围。

## 11. 上线前仍需业务确认的问题

- 本人数据的准确归属字段：创建人、业务负责人、店铺负责人、执行人是否一致；多人协作事实如何定义本人范围。
- 历史口径：调岗、组织移动和负责人更换后，旧业绩归属与历史查看权限分别采用什么政策。
- 共享业务归属：主归属、权重分摊还是多个分析视角；权重、金额舍入与跨期间调整如何校验。
- 指标字典：哪些金额可相加、哪些比率可合并分子分母、哪些评分需权重；null、不完整数据与零分母如何展示。
- 冲突和例外：是否需要显式拒绝、临时代理、仅看汇总不看明细、敏感字段、写入范围与权限配置审批。
- 生命周期：根节点是否允许删除、历史节点停用/软删除、撤销时效、在途任务、组织树版本与异常数据修复流程。
- 系统边界：共享组织目录如何映射到每个 applicationId，是否还有企业/租户边界；ALL 不得绕过这些边界。

以上未确认项不是默认开关。其他 Agent 应先定位目标系统现有契约；已有规则可复用并记录证据，没有规则时提交待决项，不得把本说明书的建议当作用户已批准的业务政策。

## 13. 本系统页面与按钮权限：实际测试流程（2026-09-05 新边界）

本节取代早期“HRM 管页面按钮”的方案。HRM 只提供系统准入，各系统角色与授权独立保存；实现可复用，但授权数据不能跨系统共用。UIModel 当前 applicationId 为 uimodel，仅模拟一个业务系统。

- 从导航栏或 A 拓扑工具栏点击“功能权限”。管理员控制台是测试恢复入口，不受测试角色限制，明确不属于生产权限后门。
- 按页面树配置：选择角色，勾选页面访问并为按钮选择三态。“允许整页”授予该页面及所有已登记按钮；页面开关本身不会隐式授予按钮。关闭页面保留按钮配置，但这些按钮不生效。
- 现场配置：选角色后进入，带虚线的真实业务按钮点击只弹权限编辑器，不执行业务动作；页面标记可配置页面访问。两种入口共用同一草稿，保存前不影响测试结果。
- 单角色测试：假定准入已通过，测试这个角色的页面和动作。人员测试：按稳定 personId 合并其全部功能角色，再判断模拟 HRM 准入；权限来源面板显示授予角色。
- A 拓扑人员卡可以分配多个功能角色。同一人员跨层卡共享角色，角色不会替代各任职的数据范围，更不会与 KA 标签混用。
- 当前七个已有页面接页面访问拦截；A 拓扑的 12 类业务动作及门户的系统入口（portal.enter）接按钮权限。其他内部业务按钮尚未接入，不能宣称全站所有按钮已经受控。全屏、缩放、展开、搜索和说明入口属于展示导航，不作为业务权限。
- 组织操作提交时再次检查动作权限。页面刷新、直接输入受限页面地址仍按已保存测试身份拦截。浏览器控制台篡改不能被前端阻止，生产必须后端执行同样检查。

- 假如 Given：调整角色权限尚未保存。
- 当 When：取消草稿或跨页面继续现场配置。
- 那么 Then：取消丢弃草稿；同标签页跨页面保留草稿但不应用到测试。保存只更新该角色，其他角色与人员标签不变。恢复权限示例明确返回管理员演示态，不修改组织名册。


### F07 按钮可见与可用分别配置【UI 已实现】
- 假如 Given：角色已获得所属页面访问权，在树或现场配置中选择某按钮。
- 当 When：选择“隐藏”“可见不可用”或“可见可用”并保存。
- 那么 Then：测试身份分别不渲染按钮、展示禁用按钮、允许使用按钮；链接类按钮禁用时移除 href 并阻止跳转。
- 存储约定：动作编码表示使用权，visible:动作编码表示展示权；使用权隐含展示。三态编辑隐藏时移除两种授权，仅可见时只保留展示权，可用时保留两种授权。旧缓存中只有动作授权仍代表可用；没有两种授权代表隐藏，不再以全局 deniedStyle 决定每个按钮的展示。
- 多角色按允许并集合并：可用 > 仅可见 > 隐藏。某角色隐藏不否决其他角色允许。父页面关闭或 HRM 准入关闭时，展示权也不能放行。页面本轮仍以“允许访问/禁止访问”配置，不新增“可见菜单但禁止访问”的独立状态。

### F08 搜索结果也可手动展开折叠【UI 已实现】
- 假如 Given：搜索“新增”筛出 A 拓扑与匹配按钮。
- 当 When：点击该页折叠箭头，再点击展开。
- 那么 Then：子按钮先收起再显示；搜索不能强制覆盖用户点击。搜索词变化时重新展开匹配结果。无已登记子按钮的页面不提供可操作展开箭头；树内关闭滚动锚定，减少收起后的视觉跳动。

### F09 门户入口现场配置【UI 已实现】
- 假如 Given：门户原有身份和目录准入允许显示系统入口。
- 当 When：现场模式点击顶部“进入工作台”、首屏进入或系统卡片进入按钮。
- 那么 Then：打开 portal.enter 三态配置，不跳转、不打开新标签；各入口共享一个权限。测试时仍同时受门户原有准入条件约束，本演示权限不会扩大 HRM 实际准入。
- 覆盖边界：本次增加门户入口动作，不代表门户管理、导航链接及其他页面全部按钮已经登记。新增权限不自动赋予旧缓存角色，须手动配置；“恢复权限示例”会重置所有演示授权，不用于保留自定义设置的升级。


## 14. 实现方式与接入手册（供后续 Agent）

### 14.1 职责和源码入口

- src/components/permissions/permission-context.ts：最小共享接口，提供 state、can、reason、inspect、launch、assign。公共 Button 只依赖该上下文与模型，避免反向依赖渲染 Button 的 Provider。
- src/components/permissions/permission-provider.tsx：状态生命周期、角色编辑草稿、树、现场检查器、角色分配、测试身份与页面守卫。ButtonAccess 是两种配置界面共用的三态编辑器。
- src/components/ui/button.tsx：permission 属性接入点；测试时隐藏或禁用，现场模式拦截点击并打开检查器。未传 permission 的按钮保留原行为，不能据此声称已纳入权限控制。

- src/components/figma-organization/figma-organization-graph.tsx、person-access.tsx、src/pages/figma-organization-page.tsx：组织按钮标记、人员功能角色入口及组织动作提交复核。src/App.tsx：三个门户进入位置共享 portal.enter。
- src/permissions.css：控制台、树、现场虚线、测试提示和弹层样式。tests/figma-organization.test.ts：复用既有测试文件覆盖权限模型。

### 14.2 状态模型和授权编码

- applicationId 固定为 uimodel，version 为 1；各业务系统应使用自己的命名空间和授权存储。
- roles 为 id、name、grants 列表；bindings 按 personId 保存 roleId 列表。功能角色按人员绑定，任职的数据范围按节点单独配置。
- entry 按 personId 保存模拟 HRM 准入；仅明确 false 拒绝，缺失在演示中假设已准入。生产缺失准入不能照搬默认放行。
- subject 为单角色或具体人员；mode 为 admin、patrol、test。draft 仅保存当前编辑 roleId 和 grants。
- 页面编码由 templatePages 派生为 page:页面ID；按钮资源登记 code、title、page。当前目录为 7 页面、13 个动作：A 拓扑 12 个，加门户入口 1 个；每个动作另有 visible:动作编码。
- deniedStyle 仅保留旧版本缓存字段与校验，不再决定按钮展示。可见性由角色的 visible: 授权控制，不能使用该旧字段实现新的配置界面。

### 14.3 判定顺序及可手算案例

1. 拒绝未登记编码；人员测试若模拟 HRM 准入为 false，立即拒绝。
2. 单角色取该角色；人员按 bindings 找到全部角色，将允许授权取并集。未绑定角色没有页面与动作权限；隐藏不是显式否决。
3. 按钮的 page 必须先获得访问授权。允许页面的角色和允许动作的角色可以不同。
4. 动作有授权则可用且可见；否则检查 visible:动作，有授权则仅可见，无授权则隐藏。已有业务禁用条件仍可使“可见可用”的按钮不能操作，例如非空节点不能删除。
5. 页面守卫与按钮判定均只使用已保存 roles；draft 不参与有效授权计算。

案例：甲角色授予 page:organization-figma 和 visible:org.create，乙角色授予 org.create。人员只持甲时可以进入 A、新增按钮可见但不能用；同时持甲乙时可新增；只持乙时因为页面不允许，不能进入 A；HRM 准入为 false 时，无论持有哪些角色都不能进入。另一个角色把新增设为隐藏不会抵消乙的允许。功能允许新增并不改变该人员的业务数据范围。

案例：角色有 page:portal、portal.enter，但没有 page:people。其门户进入按钮可以跳到人员选择地址，目的页面仍拒绝。入口动作权限不隐含目标系统准入或目标页面访问；当前模板目标是本地示例，不是正式 SSO。

### 14.4 草稿、模式与保存语义

- admin 是演示编辑态，不按测试角色限制业务 UI；patrol 展示已登记按钮并用虚线标记，点击调用 inspect，阻止原业务回调或链接跳转；test 才把已保存权限应用到界面。
- 树或现场第一次修改建立 draft；现场跨页仍使用同一份草稿。编辑期间锁定角色切换与新角色创建，避免把草稿误存到其他角色。保存只替换目标角色 grants，取消只丢弃草稿。
- 待保存计数统计变化的授权编码，不是按钮数：一个按钮从隐藏变为可用可能改变动作与展示两个编码，显示 2 项。
- 新增空角色立即保存角色本身，初始无授权；人员角色分配在单独弹窗点击保存后立即生效，不属于角色授权草稿。修改角色影响所有绑定该角色的人。
- 现场模式保存或取消返回 admin；在 test 模式改角色并保存会更新当前测试结果。已有草稿时不能开始测试。测试身份选择在 test 模式下会实时改变有效身份，“应用到真实页面”同时关闭控制台。
- 控制台是始终可到达的演示恢复工具；生产不能直接保留这一例外，必须用单独的权限管理权、审计及防止最后一个管理员被移除的机制保护。

### 14.5 存储、兼容和数据边界

- sessionStorage 键 uimodel:system-permissions:v1 保存整个 PermissionState，包括未保存草稿和测试模式；同标签页刷新、同来源导航可以恢复，不是数据库持久化，也不承诺多标签同步。
- parsePermissions 校验系统、版本、非空角色集、唯一角色 ID、已登记编码、角色绑定引用、准入布尔值和模式/草稿。损坏或不兼容缓存恢复默认示例并提示；存储不可用时保留内存状态并提示跨页可能丢失。这里恢复管理员仅适用于本地演示，不可照搬生产失败策略。
- 增加资源不会自动给旧角色授权。旧缓存中的动作授权继续表示可用；旧的无授权按钮按三态规则隐藏。恢复权限示例重建 manager/viewer、绑定、准入、模式及草稿，会丢弃自定义授权。
- 初始组织管理员拥有目录内全部权限；只读成员可进入全部页面、按钮仅可见。周林默认绑定组织管理员，田靖绑定只读成员，其余默认无功能角色。
- 测试身份下拉取 demoDepartmentData 的去重快照，不是实时 HRM 名册；当前页面新建人员可以通过卡片分配角色，但尚未同步进入该下拉，刷新后其临时组织记录也会消失。生产须统一人员 ID 与在职生命周期。
- 组织结构、数据范围、KA 标签仍保存在各自页面内存；角色授权保存不改变组织 KPI、归属关系、汇总算法或数据范围。组织与权限的“恢复”按钮互不代替。

### 14.6 新页面和新按钮的最小接入步骤

1. 新页面先按现有模板约定登记 templatePages、页面组件与路由；确认通过 PermissionPage 包裹，导航使用同一个 page: 编码。
2. 在 permissionActions 登记稳定动作 code、可读 title、所属 page；不要从按钮文本或 DOM 序号生成权限编码。同一语义的重复入口共用编码，不同业务动作分开。
3. 给实际公共 Button 传入 permission，例如 permission="org.create"；树与现场编辑会从同一目录生成。普通链接需接入受控 Button 或等效守卫，不要只改树而漏掉真实入口。
4. 给业务提交、快捷键、批量动作等实际执行入口补权限检查；不要把树的三态选择当作后端授权。现场模式也须保证不能通过重复入口执行变更。
5. 测试隐藏、仅可见、可用、页面关闭、多角色并集、直接 URL、重复入口、取消/保存/刷新以及新增权限默认未授予旧角色；补齐文档中的覆盖列表。

### 14.7 正式后端实现仍需完成的工作

- 使用真实身份与 HRM 系统准入凭据；由本系统后端维护角色、人员绑定、资源目录及授权版本，所有 API 自行鉴权，不能信任前端角色、personId、grants 或 sessionStorage。
- 每次请求同时满足准入、页面/动作授权、动作对应的数据范围与业务状态。展示授权只控制呈现，不授予读取敏感数据或写入权限；汇总与明细都要用有效读取范围。
- 保存授权需管理权限、服务器校验、审计记录、并发版本冲突控制、权限撤销与缓存失效；导出、审批等动作需独立定义资源和数据边界。
- 离职、兼任结束、组织迁移、历史事实归属及跨系统身份映射须结合前述组织 BDD 落地；这里的前端模型测试不代表这些后端场景已经实现。
- 本轮未提供角色改名/删除、临时授权到期、显式拒绝优先、字段脱敏、多系统授权切换或全站自动扫描按钮。它们不是隐藏入口；需要后续单独设计与实现。
