# PrerequisiteAction：说明动作缺少哪些条件

当一个动作必须等若干条件全部满足后才可执行，且用户需要知道如何补齐条件时，可以比较本组件。报名、导出、发布、分配都只是可能的映射；判断依据是“条件集合 → 是否允许动作”，不依赖业务名称。

网站入口：`/components?category=interaction#prerequisite-action`。真实调用示例：[prerequisite-action-example.tsx](../../src/examples/prerequisite-action-example.tsx)。先读 [通用复用方法](../UI-REUSE.md) 判断是否应与其他选择或反馈组件组合。

## 输入与输出

| 参数 | 类型和含义 | 调用方约束 |
| --- | --- | --- |
| `conditions` | `readonly PrerequisiteCondition[]` | 每项使用稳定且唯一的 `id`；`satisfied` 由真实状态派生 |
| `hint` | `string`，尚未满足时的说明 | 说明当前缺失项或下一步，随条件变化更新 |
| `onAction` | 无参数动作回调 | 由宿主接入真实请求、失败处理和结果反馈 |
| `label` | 可选 `string`，默认“提交” | 替换为目标动作名称，例如“生成预览” |
| `connectEach` | 可选 `boolean`，默认 `false` | `true` 为每个未满足条件画线；`false` 使用整体引导线 |

`PrerequisiteCondition` 包含 `id: string`、`satisfied: boolean`、`content: ReactNode`。内容可以是标签、选择控件、说明或组合布局。组件为每项创建自己的布局锚点，调用方不需要特定 `label` 层级、CSS 类名或 `data-satisfied` 属性来让连线工作。

动作可用性由 `conditions.every(...)` 推导，调用方不再另传一份 `ready`。空列表表示没有前置限制，动作可用；尚未加载、尚未判定不应通过空列表表达，应提供未满足条件或由宿主显示加载状态。

## 状态与动作时机

| 当前状态或操作 | 组件行为 | 宿主行为 |
| --- | --- | --- |
| 有任一项未满足 | 按钮禁用，显示 `hint` | 保持条件判定与提示一致 |
| 所有条件满足 | 按钮可用，显示“条件已满足，可以 + 动作名称” | 决定是否还需要业务确认 |
| 一项满足或撤销 | 对应虚线消失或恢复；可用性重新计算 | 更新真实条件源，而不是单独修改按钮 |
| 条件满足后点击动作 | 调用一次本次点击的 `onAction` | 执行操作、管理 pending/success/error |
| 条件内容尺寸改变 | 测量组件自有锚点并更新连线 | 保持稳定 ID，检查目标布局 |

`connectEach=true` 时只连接未满足项；全部满足后没有条件连线。整体引导模式在可用时隐藏引导线。虚线为装饰，设为 `aria-hidden`；真正的说明是可见文本及按钮关联的提示。

组件不保存表单字段，也不会在条件改变时自动清空宿主成功提示。若条件变化使旧结果失效，宿主应同步清理结果；如果仍然有效，则按业务保留。`onAction` 不负责等待请求结束，按钮不会自动进入提交中状态，也不自动防止第二次点击。

## 为什么这样设计

同一组条件同时决定按钮状态和引导目标，避免 `ready` 与画线依据各自维护而矛盾。稳定 ID 标识条件，组件持有锚点，使内容能换成不同控件而不依赖调用方 DOM 结构。未满足条件仍可见，让用户知道如何继续，而不只看到一个无法点击的按钮。

这是可用性与操作引导。可用按钮不代表业务授权已通过，真实动作仍由宿主和服务端检查。

## 迁移到未列举业务

1. 写出动作前必须满足的事实，区分字段有效性、用户确认和异步准备状态。完成条件：每项都有稳定 ID、可计算布尔值与可理解内容。
2. 从宿主状态派生 `conditions`，用缺失项生成 `hint`，避免另存一套可用性状态。完成条件：满足与撤销任一项时，条件和提示保持一致。
3. 把原有输入或选择组件放入各项 `content`；按需要开启逐项连线。完成条件：换成不同控件后，锚点仍由组件管理。
4. 将 `onAction` 接到宿主动作。若需要请求期间禁用，可把“当前允许执行”作为有内容说明的条件；请求错误和权限仍由宿主处理。完成条件：防重复、失败恢复和结果是否失效都有明确责任。
5. 用添加、移除、重排、撤销和窄容器验证。完成条件：规则与引导一致，不依赖业务名字或旧示例布局。

| 业务映射示例 | 条件结构 | 宿主动作 |
| --- | --- | --- |
| 导出统计 | 对象已选、期间已确认、数据已准备 | 检查导出权限、请求文件、展示结果 |
| 发布内容 | 标题有效、必填资料齐全、用户确认 | 校验版本和权限、提交发布、处理错误 |

条件数量和控件种类可以不同。若要求“至少满足两项”“任选一条路径”等规则，宿主可以把该业务规则计算成一项有明确说明的条件；如果需要组件展示复杂依赖图或分支关系，则需要新的交互契约。

## 必须保留、可以调整、宿主负责

| 层次 | 约定 |
| --- | --- |
| 必须保留 | 唯一条件 ID、所有条件共同决定可用性、撤销立即重新判定、线与缺失项一致、文字提示、原生按钮禁用语义 |
| 可以调整 | 条件数量、内容、动作名称、未满足提示、整体或逐项线模式、有作用域的颜色/间距 |
| 宿主负责 | 条件事实、异步准备、权限、请求、重复操作控制、结果反馈、状态变化后是否清除旧结果 |

当前采用浅底条件区、灰色禁用按钮和蓝色可用动作，虚线从按钮指向条件。颜色可按目标主题调整；保留可见的禁用区别和文字解释。布局在窄屏堆叠，逐项连线依据尺寸测量；复杂内容、浮层、长文案和容器裁切需在目标页面检查。

## 键盘及尚未支持的能力

动作是原生按钮，可用时支持 Tab、Enter 和空格，禁用时遵循浏览器原生行为。条件中的键盘操作由各自控件提供；调用方仍须为输入、复选和选择控件提供名称及标签。组件不会替任意 ReactNode 自动补齐无障碍语义。

当前不提供表单验证引擎、条件依赖图、自动聚焦首个缺失项、真实请求、权限系统、提交中状态、重试或结果存储。连线依赖浏览器布局和 ResizeObserver；纯服务端渲染的静态 HTML 不构成连线布局验收。

## 复制清单

同仓库使用真实示例中的入口。跨项目复制本体、连线样式及基础按钮；`content` 中使用的其他组件还需各自的复制清单。

| 角色 | 必需文件 |
| --- | --- |
| 实现入口 | `src/components/ui/prerequisite-action.tsx` |
| 布局和连线样式 | `src/components/ui/prerequisite-action.css` |
| 基础按钮及样式 | `src/components/ui/portable-button.tsx`、`src/components/ui/portable-button.css` |

直接从独立入口导入，无需复制 `form-controls.tsx`、门户 CSS 或权限模块。如果内容使用 TriStateCheckbox，另带 `src/components/ui/tri-state-checkbox.tsx` 和 `src/components/ui/tri-state-checkbox.css`，以及该控件使用的 Lucide 图标。使用 SearchSelect 等组件时同样追加其闭合清单。

核心运行需要 React；真实示例中添加的选择控件或图标依其自身清单处理。局部样式含盒模型及焦点规则，字体继承宿主。可将基础按钮适配为宿主已有 React/shadcn UI 按钮，保持事件、禁用、提示关联和普通按钮语义，并同步适配样式中的 `.portable-button` 选择器。

## 迁移验收

- 缺失四项时四条逐项线，逐项满足后减少，全部满足后可执行；撤销任一项立即恢复对应线和禁用。
- 改变条件数量、顺序及内容标签结构，线仍指向相应条件，未依赖外部 class 或 DOM 选择器。
- 空列表按“无限制”处理；加载中不会被错误表达为空列表。
- 请求期间重复点击、失败恢复和旧结果失效由宿主处理，并观察实际效果。
- 键盘能完成条件输入和动作；窄容器、长内容及尺寸变化后引导仍可理解。
- 用未在说明中列举的业务写出条件来源、动作职责和扩展边界。

这些是待执行的验收场景，实际结果记录在 [ACCEPTANCE.md](../ACCEPTANCE.md)。
